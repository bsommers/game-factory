# Parity scenarios (spec/v4/parity)

Language-neutral scripted-input scenarios with the JS reference trajectory attached, so a port (Godot today) can be diffed against `templates/web-project/src/lib/*.js`. Other tracks keep their own subfolders here (`ai3d`, `animgraph`, `limb3d`, ...); this section covers `locomotion3d/` and `camera3d/`.

## Files
`spec/v4/parity/{locomotion3d,camera3d}/<name>.json`, generated by `node spec/v4/parity/gen.mjs` (`--check` fails when a committed file is stale; `test/godot-locomotion.test.mjs` runs that check). Never hand-edit `expected`.

```
{ kind: "locomotion3d" | "camera3d", name, description,
  config: "../../examples/<kind>/x.json" (relative to the scenario file) | inline partial object,
  world, start, yaw, settle, sampleEvery, script: [segments],
  tolerance: {default, pos, speed, vy, yaw | target, fov, distance, roll},
  expected: { dt, steps, samples: [{step, ...}], events: [{step, event}] } }
```

### locomotion3d scenario
Mirrors `locomotion3d.simulate`: 30 settle steps with no input, then the script at `dt = 1/60`. Segment: `{frames|seconds, move:[x right,y fwd], camYaw, sprint, jump (first frame), jumpHeld, dodge (first frame), impulse:[x,y,z], stun}`. `world` is `flat` or `{kind: ice|conveyor|river|platform, ...}` (the flat-floor worlds of `factory-core/locomotion3d`; `wall` and `ramp` need a real collision world and are not part of the pure-core parity). Samples hold `state, pos, speed, vy, yaw, grounded, invulnerable` at every `sampleEvery`-th step, the last step and every step with an event; `events` lists every event with its step.

### camera3d scenario
`start` is the first target (player feet), `yaw`/`pitch` optional. Segment: `{frames, target (teleport), velocity:[x,y,z] m/s (target += v*dt each frame), yawDelta, pitchDelta (rad per frame), lock:[x,y,z], aim, trauma, fovKick (first frame)}`. `world` is absent or `{kind: "wallZ", z}` (box `x +-50, y -1..20, z..z+1`, boom swept against its -Z face). Samples hold `pos, target, fov, distance, roll, collided`.

## Tolerance policy
Both sides use IEEE doubles (Godot cores use plain `float`, never `Vector3`, which is 32-bit) and the same operation order, so trajectories agree to the rounding of the stored data: the stored `expected` is rounded to 1e-9, the measured max error is about 5e-10. Committed tolerance is 1e-6 (m, m/s, rad, deg) for every numeric channel; `state`, `grounded`, `invulnerable`, `collided` and the full event list (step and name) must match exactly. A port that fails by more than 1e-6 has a logic difference, not a rounding one.

## Running
- JS side: `node spec/v4/parity/gen.mjs` (regenerate) / `--check`.
- Godot, whole suite: `godot.test {project: templates/godot-action3d, runner: res://tests/run_locomotion.gd}` (`test_parity.gd` finds `../../spec/v4/parity` relative to the project, or `FACTORY_PARITY_DIR`; it skips when neither exists).
- Godot, one scenario: `godot --headless --path templates/godot-action3d --script res://tests/locomotion/parity_cli.gd -- --scenario=/abs/x.json [--out=/abs/godot-trajectory.json]` prints `PARITY <name> ok|FAIL maxErr={...}` plus per-sample errors and exits 0/1 (2 = unreadable). `--out` writes the Godot trajectory as `{steps, samples:[{step,...}], events, maxErr}` for external diffing.
- A parity capability can consume the same files: run the reference JS (or trust `expected`), run `parity_cli.gd`, compare using `tolerance`.

## Ports under test
`templates/godot-action3d/scripts/locomotion/locomotion_core.gd` and `scripts/camera/camera_core.gd`: pure steppers; the same decision logic drives the real game through a pluggable mover (`player_controller.gd`, CharacterBody3D + `move_and_slide`) and boom sweep (`camera_rig_controller.gd`, physics sphere cast). Engine physics is not expected to match `collision3d` bit for bit; the pure cores are what parity covers.
