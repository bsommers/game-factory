# Plan: Go, Rust and Python game support, multi-language access, standalone apps

Status: proposal. Nothing here is implemented. Written 2026-11-21 from a survey of the repo at `0d531eb`.

## 1. What the factory supports today

| Layer | Languages | Where |
|---|---|---|
| Game targets | **GDScript** (Godot 4.x) and **JavaScript** (zero-dependency browser games, ES modules + Canvas) | `templates/godot-project/`, `templates/web-project/`; `project.new` takes only `web: boolean` |
| Factory itself | Node ESM (`.mjs`), shell | `factory-core/`, `bin/factory`, `api/`, `mcp/`, `swarm/` |
| Python | **Tooling only**, not a game target: Blender builders, audio synth, STL checks | `examples/ratops/*.py`, `tools/blender_ipc/`, `tools/print/` |
| Go / Rust | None | no template, kit, lib, doc or skill mentions them |

So Python is here but only as asset tooling. There is no way to scaffold a Go, Rust or Python game, and the gameplay engines (`templates/web-project/src/lib/`: platformer-physics, hazard-kit, world-gen, autopilot-kit) and content kits exist only in JS.

Standalone apps: **partly done.** `tools/web/pkg/package-desktop.mjs` already packages web games on **Neutralinojs** (a ~3 MB prebuilt binary over the OS webview; 1 MB downloads, versus 85-110 MB for Electron; see `docs/BUILD-WEB-DESKTOP.md`). Godot games export through `tools/build.sh`. What is missing is a registry capability, a choice of shell, and anything for Go/Rust games.

The thing you were thinking of is probably **Tauri** (Rust, OS webview, a few MB). Neutralino is already smaller. Tauri's edge is signing, updater, plugins, mobile targets and a real Rust backend, not size. **Wails** is the Go equivalent. Both are covered below.

## 2. Interpreting "accessible in multiple languages"

Two readings, and the plan covers both. Confirm which one matters most before phase 4:

- **A. Build games in more languages** (Go, Rust, Python). Phases 1-3.
- **B. Drive the factory from more languages** (Go/Rust/Python clients for the capability registry). Phase 4. Cheap: the registry already emits OpenAPI and MCP.

## 3. Design principles

1. **One registry, one envelope.** New behavior is a capability in `factory-core/` returning `{ok,data,error,next}`; CLI, HTTP, MCP and import pick it up (per `AGENTS.md`). No language-specific side doors.
2. **Language is an axis, not a fork.** `project.new` gains `lang` and keeps `web` as an alias for `lang: "js"`. Existing calls and exit codes do not change.
3. **Spec first, ports second.** Ports are only trustworthy if they match. Each shared engine gets a language-neutral spec plus golden JSON vectors; every port must pass them in CI.
4. **Reuse before rewrite.** Rust and Go can compile to WebAssembly and ride the existing web build, screenshot, smoke and Neutralino pipeline. Native targets are additive.
5. **Never weaken a gate** (`layered-verification-gates`). A port that cannot pass the vectors is not shipped.

## 4. Phases

### Phase 0: language axis and discovery (small, do first)
- New capability `languages.list` / `languages.show`: id, kind (`game` or `client`), toolchain probe (`go version`, `rustc --version`, `python3 --version`), template path, supported packagers, status (`stable|preview`).
- `project.new {lang}` enum `gdscript|js|go|rust|python` (default unchanged). Unknown lang returns `BAD_INPUT` listing valid ones. Scaffolding moves from `bin/factory-scaffold.sh` branches to per-language template dirs (`templates/go-project/`, `templates/rust-project/`, `templates/python-project/`) with the same `sync` semantics.
- `project.run` tasks (`test|build|shot|check-imports`) dispatch by detected project kind (`go.mod`, `Cargo.toml`, `pyproject.toml`) instead of `package.json` vs Godot only.
- `guide.route` and `guide.plan` learn language: skill/kit ranking filters by `lang`; `guide check` gets per-language checks.
- Docs: `docs/LANGUAGES.md` (matrix), `AGENTS.md` and `README.md` layout tables, regenerate the skill index. Tests: extend `test/factory-surface.test.mjs` so the four doors agree on `languages.list` and `project.new {lang}`.

### Phase 1: shared spec and conformance vectors
- `spec/` directory: `rng.md` (pick one bit-exact PRNG, e.g. PCG32 plus a splitmix seeder; JS `Math.random` and Go/Rust std RNGs are not portable), `platformer-physics.md`, `hazard-kit.md`, `world-gen.md` (including the fairness validator), `autopilot.md`.
- `spec/vectors/*.json`: inputs and expected outputs generated by the existing JS engines at a pinned commit, committed, and regenerated only deliberately. JS stays the reference implementation.
- Fixed-step integer or fixed-point where float drift would diverge across languages; document tolerances where floats remain.
- Style presets (`styles/`), library registry and `defs.artManifest()` are already JSON, so they are consumed as-is by every language. Do not duplicate them.

### Phase 2: Rust target
- Template `templates/rust-project/`: cargo workspace, `crates/engine` (ports of the four libs, `#![forbid(unsafe_code)]`), `crates/game`, `tests/vectors.rs` consuming `spec/vectors`.
- Framework: **macroquad** for the default 2D template (small API, easy for swarm agents, builds to wasm); **Bevy** as an opt-in `--ecs` variant for larger games. Decide after a one-day spike; record in an ADR (`defending-architecture-decisions`).
- Build outputs: native (`cargo build --release`, per-target) and `wasm32-unknown-unknown` plus a thin HTML shell, which flows into the existing web build, `shot.mjs` and `smoke_web.sh`.
- Gates: `cargo fmt --check`, `clippy -D warnings`, `cargo test`, vectors. `CARGO_TARGET_DIR=/datanapps/cargo-target/<project>` (never `/tmp`, per global instructions).

### Phase 3: Go target
- Template `templates/go-project/`: `go.mod`, `internal/engine` ports, `cmd/game`, `engine/vectors_test.go`.
- Framework: **Ebitengine** (2D, cross-platform, wasm support, pure-Go on most platforms so `CGO_ENABLED=0` cross-compiles are realistic on Windows and macOS targets; verify per platform).
- Outputs: native cross-compiled binaries via `GOOS/GOARCH`, plus `GOOS=js GOARCH=wasm` into the same web pipeline.
- Gates: `gofmt -l`, `go vet`, `go test ./...`, vectors, `-race` on engine tests.

### Phase 3b: Python target (lower priority)
- Template with **pygame-ce**, `uv`/`venv` outside `/tmp`, `pytest` vectors, ports of the engines. Standalone via PyInstaller or Nuitka. Python is last because it is the slowest runtime and the weakest fit for wasm; the existing Python (Blender/audio) stays tooling and is unaffected.

### Phase 4: Use the factory from Go, Rust and Python (reading B)
- The registry already serves `GET /openapi.json`. Add `factory clients generate --lang go|rust|python --out <dir>` (capability `clients.generate`) that emits a typed thin client from the OpenAPI document, using the existing HTTP surface (127.0.0.1) so there is still one implementation.
- Generated code is checked in under `clients/<lang>/` only if a drift test (`regenerate and diff`) is green, so it cannot rot. Each client implements the envelope, the stable `error.code` set and SSE progress.
- MCP stays the entry point for agent hosts; these clients are for tooling and custom orchestrators.
- Docs: add a language column to the "same task four ways" table in `docs/SURFACES.md`.

### Phase 5: standalone applications (can start in parallel with Phase 2)
New capability `package.standalone` (`project`, `shell`, `platform`, `version`, `out`), returning artifact paths and SHA-256s; CLI `factory package <dir> --shell ... --platform ...`. It generalizes `package-desktop.mjs` and wraps `tools/build.sh`.

| Project kind | Default shell | Alternatives | Notes |
|---|---|---|---|
| JS web game | **Neutralinojs** (existing, ~1 MB) | **Tauri v2** (`--shell tauri`), Electron (`--shell electron`, opt-in, warns about size) | Tauri adds updater/signing/mobile; needs Rust toolchain; builds are per-OS, so CI matrix |
| Rust (native) | none, a plain binary | Tauri only if you want a webview UI | Smallest result; static where possible, strip, LTO |
| Rust/Go (wasm) | reuse the web pipeline, then any web shell above | | One build, every shell |
| Go (native) | none, a plain binary | **Wails** if there is a webview UI | `CGO_ENABLED=0` where the framework allows |
| Godot | Godot export (existing `build.sh`) | | Add checksums and the same archive layout |
| Python | PyInstaller or Nuitka | | Largest; document honestly |

Common pieces: one archive naming scheme (`<name>-<ver>-<os>-<arch>`), `SHA256SUMS`, reproducible mtimes (already in the Neutralino packager), pinned and checksummed upstream downloads, a size report, per-shell smoke scripts modeled on `smoke_linux.sh`, and documented signing (macOS notarization, Windows signing) as a manual, secret-gated release step. Update `docs/BUILD-WEB-DESKTOP.md` with a measured size table once Tauri is built here; do not publish Tauri/Wails sizes until measured.

## 5. Verification and CI
- New `test/` coverage: `languages.list` and `project.new {lang}` across the four doors; scaffold each language into a temp dir and run its own test task; vector conformance for every port; clients drift test; `package.standalone` unit tests with a stub shell, plus real smoke runs where a toolchain exists.
- Toolchains are probed, not assumed. This machine currently has `go`, `rustc`/`cargo` and `python3`; tests for a missing toolchain report `SKIP` with the reason, never a silent pass.
- CI matrix (first-party actions only, per `hardening-ci-workflows`): linux for all, plus windows/macos for packagers. Windows smoke stays on the local VM as today.

## 6. Risks
- **Port drift** between JS, Rust, Go: mitigated by the vectors gate and keeping JS as the reference.
- **Float divergence** across languages: use fixed-step and documented tolerances; PRNG must be integer-only.
- **Scope**: three languages plus packagers is large. Order by value: Phase 0, 1, Rust (2), packaging (5), Go (3), clients (4), Python (3b).
- **Webview variance** (WebKitGTK vs WebView2 vs WKWebView) affects every non-Electron shell; the single-file HTML fallback stays.
- **Toolchain versions** (Tauri, Wails, Ebitengine, macroquad, Bevy) move fast: pin and checksum at implementation time and re-verify APIs then; this plan names no versions on purpose.

## 7. Decisions needed
1. Reading A, B or both (section 2). Recommendation: both, in the order above.
2. Rust 2D framework: macroquad default with Bevy opt-in (recommended) vs Bevy only.
3. Is Tauri worth adding next to Neutralino? Recommendation: yes as an opt-in shell, keep Neutralino as the default for size.
4. Is Python a game target, or does it stay tooling and a client language only?

## 8. Addendum (2026-11-21): decisions and scope additions

Decisions (from the owner): readings A and B both; macroquad default with Bevy opt-in; Tauri as an opt-in shell next to Neutralino; Python is both a game target and a client language. Work happens on branch `multilang`; tag `pre-multilang` marks the prior state and `main` is untouched.

### Phase 6: physics and collision (v2 engines)
The existing engines are platformer-specific (one-way platforms, ropes, pits) and stay **frozen** as v1 so the ports match their vectors. New general-purpose engines are additive:
- `collision2d` / `physics2d`: shapes, SAT manifolds, ray/shape casts, swept CCD, spatial-hash broadphase, tilemaps, sequential-impulse rigid bodies, joints, sleeping, character controller, snapshot/restore for rollback. Spec + vectors in `spec/v2/`.
- `collision3d` / `bvh`: 3D primitives, ray and swept queries, SAH BVH with a documented flat buffer layout, capsule character controller. Spec + vectors in `spec/v3/`.
- Ports of v2/v3 to Rust, Go and Python follow the same vector-gated process as Phase 1-3, after the engines settle.

### Phase 7: advanced rendering and ray tracing
Build-vs-pull-in table and decision live in `docs/RENDERING.md`. Default is to build, zero runtime deps for games; third-party options (e.g. three.js path tracer) are opt-in.
- `tools/render/`: deterministic multi-threaded CPU path tracer for baking sprites, lightmaps/AO and hero art, with PNG output.
- `raytrace-kit`: browser WebGPU compute tracer over the flat BVH buffer, with a WebGL2 SDF ray-march fallback and graceful degradation.
- `render.trace` / `render.info` capabilities on all four surfaces.
- Follow-on (not started): Rust (wgpu) and Go tracer ports; hardware RT (Vulkan/DXR) as future work.
